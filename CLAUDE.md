# aintercept: notes for coding agents

- **Setting aintercept up for someone** (a fresh clone to the People page with live Claude Code traffic): follow `docs/SETUP.md`. `make up` starts everything, `make verify` proves it, and routing Claude Code (step 4) needs the person, because it uses sudo.
- **The data pipeline** is `docs/PIPELINE.md` (v9): the observer streams raw files to the object store (`<prefix>/raw/`), `aintercept worker` loads them into Postgres's fact tables and refreshes the rollups, and the API reads Postgres (and a call's raw member, one ranged GET). The schema is hand-written (`aintercept/internal/pg/schema.sql`). The API tests load their datasets the same way (`aintercept canon -raw`, then `canon -load`).
- **Before every commit, run `make check`.** It runs exactly the checks CI requires. A commit that fails it won't go green. It needs Docker: the Postgres tests run in the pinned image (`scripts/test-pg.sh`, or a server you name in `AINTERCEPT_TEST_PG`).
- **UI and query API work** (`ui/`, `api/`): follow `docs/ui/BUILD_PLAN.md`. It overrides the design handoff in `docs/ui/handoff/`, and §11 lists every automated rule.
- **The definition of done is `docs/ui/requirements.json`.** Building a component means a story for each state listed there; implementing an endpoint means a sample for each scenario.
- **Precompute everything** (`docs/PIPELINE.md` §5, §6). The workers' rollups hold every value that would aggregate many rows. An API endpoint does indexed reads (tens to a few hundred rows) and applies `now()`. A new UI value that sums history means a new rollup column, never a scan in an endpoint.
- **Never hand-write API types or samples.** Change the Pydantic models or tests in `api/`, then run `make regen`.
- **The UI needs Node 24:** run `nvm use` in `ui/`.
- **The Interceptor** (the control-plane hook, `docs/INTERCEPTOR.md`): the contract is `aintercept/interceptor/v1/interceptor.proto`, or v2 (`aintercept/interceptor/v2/interceptor.proto`, `docs/INTERCEPTOR_V2.md`: each call's new messages) per deployment. After changing it run `make proto`; `make test-interceptor` runs observe and enforce end to end through a real Envoy (needs Docker).
- **Adding a provider or harness:** follow `docs/PROVIDERS.md`, the list of every place it touches (routing, credentials, identity, parsing, the Interceptor, the pipeline, docs). Its rule: every transformation, extraction and callback has a unit test on an anonymized real capture, one per extracted field per traffic shape.
- **Harness parity:** `docs/harness-parity.md` tracks what each coding harness (Claude Code, Codex, …) sends, how it maps onto the common schema (common / mapped / bespoke), and what AIntercept shows. Update it whenever a capture shows something new or support lands.
- **Never commit captured traffic or real identifiers.** `data/` is gitignored, and `scripts/check-real-data.py` enforces the rest.
- **Everything scales with traffic; nothing is a single process.** Ingest scales on throughput, processing on lag, the API on usage. Each stage takes only what's new (delta in) and ends with tables that equal one pass over all the records, and its cost per record never grows with history, session size or pod count. Before building any stage, write its scaling budget into the design: work per record, state held, what it's sharded by, and anything that waits on a single point. Get the design reviewed adversarially before writing code. The design is `docs/PIPELINE.md`.
