# aintercept UI: build plan

The working agreement for building the person / session / request UI. Read this before any UI or query-API work; it records decisions that override the handoff where they differ. The design source is `docs/ui/handoff/` (start with `AINTERCEPT_UI_HANDOFF.md`).

Status and next step are at the bottom (§9). Keep them current.

## 1. Goal

A first user points their coding agent at this repository. The agent brings up the stack locally, routes Claude Code through it and trusts the CA. The user opens a local browser and watches their own traffic arrive. "Live" means within about a minute.

Local only for now. Exposing it from a Kubernetes deployment is deferred (§8).

## 4. The contract and sample-data loop

Adapted from `django-app-template` (its `write_response_to_ts_file` fixture, drf-spectacular → openapi-typescript, `make regen`):

1. **Endpoint:** a FastAPI route with a Pydantic `response_model`. The model is the contract.
2. **Scenario tests:** pytest builds a small NDJSON dataset with builder helpers (rows shaped exactly like the observer's), loads it into DuckDB, and calls the endpoint. Each endpoint has named scenarios:
   - list endpoints: at least `empty`, `one`, `many`;
   - single-object endpoints such as `/status`: one scenario per state the UI renders (`waiting`, `receiving`, `delayed`, …);
   - every endpoint: the edge cases the UI must render (`coverage_gap`, `pre_parser`, `live`, `not_captured`, …);
   - error responses: `write_sample(..., status=500)` gives the typed `ErrorResponse` sample that MSW's error mode serves.
3. **Sample writer:** a fixture `write_sample(response, scenario)`. With `pytest --write-samples` it writes `ui/src/api/samples/<endpoint>/<scenario>.ts`:
   ```ts
   import type { components } from "../../spec";
   const sample: components["schemas"]["PersonSessionsResponse"] = { ... };
   export default sample;
   ```
   On a normal test run it does nothing.
4. **Types:** `make regen` exports OpenAPI from the app, runs `openapi-typescript` to produce `spec.ts`, then regenerates samples. A changed API shows up in the samples and as type errors in stories and components.
5. **Real data:** one more scenario per endpoint, `demo`, generated from the actual captured data and passed through `extractor/sanitize.py` (consistent fake IDs, names, emails and IPs). Real captured data never lands in the repo unsanitized.
6. **Consumption:** stories import samples directly as props/args (as the template does). MSW handlers serve the same samples and add the latency/error modes from handoff §6A.11.
7. **Staleness check** (stronger than the template): `make check-generated` runs `make regen`, then fails if the generated files differ from HEAD, if any are untracked, or if they don't typecheck. CI runs it with `make test-ui` on every PR touching `api/` or `ui/` (`.github/workflows/ui.yml`).

Unknown values are `null` in the models and render as `—`. Fields that need observer extraction (tool targets, flag attributes, byte counts, session state) return `null` until that work lands; the samples update with `make regen`.

## 5. Local stack

`make up` runs Envoy (real upstream), certsvc, the observer and the processor in Docker, and the query API and the UI on the machine; `make verify` proves the path; `make down` stops it. `docs/SETUP.md` is the walkthrough.

- **Telemetry path (§7.1):** the observer writes body-stripped NDJSON to a local directory with the same `dt=/hour=` layout it uses in object storage. The query API reads that directory with the same DuckDB globs it would use against S3.
- **Routing a machine:** `scripts/route-claude-through-proxy.sh` with `127.0.0.1` (IPv4 and the `::ffff:` IPv6 entry), the CA trusted, `NODE_EXTRA_CA_CERTS` set.
- **First-user onboarding:** a root `CLAUDE.md` plus a setup doc that an agent can follow end to end, written last (M8) and tested on a clean machine.

## 7. Decided 2026-11-05 (were open)

1. **Local telemetry path:** the observer gets a local partitioned file sink (body-stripped, same `dt=/hour=` layout as object storage). No MinIO.
2. **Content locally:** off by default (metadata only; the drawer shows shapes + `NOT RETAINED`). An opt-in flag on the local stack keeps prompt/response bodies so the drawer's retained view works. Matches the positioning: not logged out of the box, available when the operator turns it on.
3. **Old console:** delete `console/` and `etl/` (and their docs/Makefile references) once `api/` covers them.
4. **Branching:** one branch, `ui`, and one PR into `main`. Each milestone is one or more commits on that branch (`ui: M0 …`, `ui: M1 …`).

## 7.5. Decided 2026-11-06: the data pipeline

The query API was parsing raw JSON on every request: `/overview` and `/people` took about 3 s, and the largest session about 10 s, on the real capture. The plan was always: capture raw first, build the UI, then shape the data to what the UI needs. The UI now says what that is.

1. **Shape at ingest, not at query time.** The API is a reader and does no parsing.
2. **Two stages.** Stage 1 runs in the observer and shapes one request at a time. Stage 2 is a downstream processor for anything that spans requests; `docs/architecture.md` already keeps cross-request rollups out of the observer.
3. **One Go binary, run in modes:** `aintercept observer`, `aintercept certsvc`, `aintercept process`. One module, one image, one mode per pod. Each pod's secrets stay its own: the CA key only reaches certsvc pods. The test fixture stays a separate module, out of the production binary.
4. **Raw stays the source of truth.** When the UI needs a new shape, stage 2 rebuilds its tables from raw.

   **Reaffirmed 2026-11-11, and widened: precompute everything** (`docs/architecture.md`, Decision 4). The API was still deriving almost everything from thin tables. Stage 2 now writes every value the UI shows, and the API only queries.

5. **Keys between the shaped tables.** Every table has a primary key, and every reference to another table is a named foreign-key column, so any row traces to its person, session, prompt and call, and back to the raw rows it came from. The keys are ids the traffic already carries, never ones we invent:

   | Table | Primary key | References |
   |---|---|---|
   | `people` | `person_id` (the account uuid) | |
   | `devices` | `device_id` | `person_devices (person_id, device_id)`: one person, many devices |
   | `sessions` | `session_id` (`x-claude-code-session-id`) | `person_id` (null: unattributed) |
   | `prompts` | `prompt_id` (`x-claude-code-prompt-id` = `cc_prompt_id`) | `session_id` |
   | `calls` | `call_id` (the `correlation_id`) | `session_id`, `prompt_id`, `person_id`, `device_id`; also unique on `request_id` (the provider's) and `client_request_id` |
   | `events` (analytics) | `event_id` (the client event's own id) | `session_id`, `prompt_id`, `person_id`, `device_id`, and `call_id`, resolved through the event's `requestId` / `clientRequestId` |
   | `coverage_gaps` | `(session_id, from)` | `session_id`; its events are those whose `call_id` didn't resolve |

   - **Lineage:** every shaped row keeps `correlation_id` and `source_file`, so it leads back to its raw rows.
   - **Unresolved references** are null, never guessed. An analytics event whose `requestId` matches no captured call is exactly a coverage gap, so a null `call_id` is a finding, not lost data.
   - **Checked, not just declared:** stage 2's tests assert that every non-null foreign key resolves to a row. DuckDB's enforced foreign keys would block the bulk reloads, so the guarantee comes from the tests.

## 8. Deferred

- Exposing the UI from a cluster: `kubectl port-forward` to the API/UI service is the simplest path (no SSH tunnel needed); auth only matters once it's reachable by more than one person.
- Other agents (Codex, ChatGPT web, claude.ai): types and colors are reserved; data shapes come later.
- The AIntercept public export (README draft in the session scratchpad).

- **M7c (2026-11-06): `aintercept process`.** `aintercept/internal/process`: raw partitions to Parquet tables (`requests`, `events`, `sessions`, `prompts`, `person_devices`, `people`), keyed as in §7.5, with `pending` and `ledger` as processor state. Dependency: `parquet-go` v0.32.0 (2026-08-10; its new indirect modules are all older).
  - **Finding files:** polls every 10 s (5 s locally). A poll lists each pod folder of the current and previous hours only after the last file it processed there (a pod names its uploads in order; S3 `StartAfter`), so it costs the new files, not the hour's. The ledger still decides: whatever is listed and not in it is processed, in any order, and a full listing at start and hourly catches anything a cursor passed (a file that became readable later).
  - **Exactly once:** a run writes its parts and snapshots, then commits by writing `manifest.json`; readers use only what it names. An uncommitted run's files are removed at the next start and its raw files processed again. Replaced files are deleted after a 5-minute grace (wall clock).
  - **Sessions that grow:** session, prompt and device rows are snapshots rewritten each run; their columns are counts, sums, minimums and maximums, so the order rows arrive in doesn't change them. A transaction whose rows span files waits in `pending` (committed with each run); end markers stop late parts of a finished transaction from writing it twice (6 hours of data time; rebuilt from `requests` at start, not committed). A transaction written without its ending, because it waited past those 6 hours, keeps its marker for 7 days, committed in `pending` (`done` and `expired`), so its ending arriving late, across restarts, is dropped rather than written as a second row.
  - **What it relies on:** a transaction's rows come from one observer pod, and a pod uploads its batches in order. Pods may arrive in any order relative to each other.
  - **Tests** (`processor_test.go`): incremental runs over shuffled per-pod uploads, with restarts, compaction and a file found only by the full listing, equal one full rebuild (5 seeds); sessions grow as files arrive; every key resolves; a crash before commit is redone; an unreadable file is retried when it changes; older rows take timing from their headers; replaced files are collected after the grace. Each guard was checked by breaking it and seeing a test fail.
  - **`aintercept replay`:** streams an existing capture (local copy or `s3://bucket/prefix`, read only) back through the processor: each pod's events in order, pods interleaved by time with a random upload lag, re-batched into uploads of `-batch-events` events, polling after each, restarting at random. It then rebuilds the same files in one pass and reports differences per table and key, plus the key check. One event per upload is for slices of the capture; the whole capture runs at observer-like batches. First real run: hour 2026-11-06T20 (27,966 events), one event per upload, a poll after each and 146 restarts: identical to the rebuild, every key resolves, 4 min 37 s.

### Processor startup at scale (built 2026-11-07)

Today `aintercept process` reads two things at start, and both grow with all of history: every ledger part (one row per raw file, about 1,000 a day), and every request part, to rebuild the end markers. At today's volume that's seconds; at a year of a team's traffic it would be minutes. The plan keeps startup bounded by recent data, whatever the total:

1. **Read only the recent request parts.** End markers only matter for 6 hours of data time (7 days for WebSockets). The manifest records each part's data-time range, and start reads only the parts that overlap that window, and only the four columns markers need (`correlation_id`, `start_ns`, `end_ns`, `ws_turn`).
2. **Compact by data day.** Small run parts merge into one file per day, and a finished day is never rewritten. History becomes a few large files that start never opens, and the API reloads only the day a compaction touched, instead of the whole table.
3. **Seal old partitions.** Raw files land within minutes of their batch, so a day more than 3 days old is complete. The manifest marks such days sealed; the full listing skips them, and start loads only the ledger for unsealed days. A file that does land in a sealed day is still found by a `make` target that sweeps everything on demand.

Done when a test that commits a year of synthetic parts shows start reading only the last week's, and the incremental-equals-rebuild tests still pass.

Built as planned (`aintercept/internal/process/days.go`). The on-demand sweep is `PROCESS_SWEEP_ALL=true` (with `PROCESS_ONCE=true` for one pass). The API swaps only the parts a compaction replaced: fact rows carry their part's `filename`. Tested by `TestStartupReadsOnlyRecentParts` (60 days built a file at a time with frequent compaction: equal to a rebuild, settled into day files, and a restart reads only parts in the marker window and unsealed ledger days) and `TestSweepFindsAFileInASealedDay`; each guard was checked by breaking it. On the real two-week capture a restart takes 1.1 s (was 1.6 s); the gap grows with history. Manifests written before this have no part ranges, so their parts count as run parts and the first compaction regroups them into day files: no migration step.
